# خطة إعادة بناء SmartBot الشاملة — محرك Facebook MCP + تصميم عالمي

> **إعداد:** فحص فعلي كامل بالـ clone والـ grep لأربعة مستودعات (SmartBot، facebook-mcp-server،
> LiveCharts2، scroll-craft) + تشغيل فعلي للباك-إند محليًا للتحقق من سلامة الاستيراد.
> **الوجهة:** هذا الملف مُعَدّ ليُلصق في Claude CLI كسلسلة أوامر تنفيذية. أنا (Claude في
> المحادثة) لم أنفّذ أي تغيير على الكود أو أي عملية على Vercel/Neon — فقط فحصت وخططت.
> **لا تستعجل التنفيذ:** كل مرحلة بوابة موافقة صريحة قبل الانتقال للتي تليها.

## 0. ملخص تنفيذي

المشروع حاليًا (36MB، ~16,400 سطر Python، ~7,900 سطر TypeScript، 23 صفحة داشبورد) **ليس مشروعًا
فاشلاً يحتاج رميًا وإعادة بناء من الصفر حرفيًا** — هو منتج SaaS متعدد المستأجرين ناضج نسبيًا
(نظام أدوار، اشتراكات، فوترة بمزودي دفع ليبيين، CRM، تدفقات أتمتة، تقويم محتوى، بث جماعي،
تقارير PDF...) أصابه **حادثتان متراكبتان**: (أ) حادثة `force-push` مباشرة قبل هذا الفحص أعادت
المشروع لنسخة قديمة بواجهة Vite/SPA ثم أُعيد ترميمها جزئيًا لـ Next.js، و(ب) دَين تقني متراكم
من محاولات ترقيع متتالية (نظامي هجرة قاعدة بيانات متوازيين، ملفات ثابتة قديمة لا تزال محفوظة في
git رغم مخالفتها الصريحة لقواعد `CLAUDE.md` الخاصة بالمشروع نفسه، تناقض في طوبولوجيا النشر).

الخطة أدناه **لا تعيد كتابة كل شيء من الصفر** — هذا سيكون قرارًا مكلفًا وغير مبرَّر تقنيًا نظرًا
لحجم المنطق التجاري السليم الموجود بالفعل. بدلاً من ذلك:

1. **تُعيد بناء طبقة تكامل فيسبوك بالكامل** حول عقد أدوات `facebook-mcp-server` (اسم كل أداة،
   شكل كل مدخل/مخرج) لكنها تُنفَّذ من الصفر بجودة إنتاجية حقيقية — لأن الكود الأصلي هناك تجريبي
   بحت (sync، مستأجر واحد فقط، بلا معالجة أخطاء) ولا يصلح للتشغيل مباشرة في منتج SaaS متعدد
   المستأجرين. هذا القرار مفصّل بالكامل في §3.1 مع البديل المرفوض ولماذا.
2. **تُصلح وتوحّد** كل نقاط الدَّين التقني المكتشفة فعليًا (وليس افتراضًا).
3. **تعيد بناء النظام البصري بالكامل** مستلهمة من `LiveCharts2` (حِرفية الرسوم/المؤشرات) و
   `scroll-craft` (معايير التصميم الاحترافي ومبدأ "قائمة الرفض" لأنماط تصميم AI النمطية).
4. **تُثبّت طوبولوجيا نشر واحدة واضحة على Vercel + Neon Postgres** بدل الغموض الحالي.

## 1. القواعد الحديدية الدائمة (تُورَث تلقائيًا في كل مرحلة أدناه، بلا استثناء)

هذه امتداد وتشديد لنفس القواعد التي وضعتها بنفسك في `smartbot-incident-recovery-roadmap.md`
بعد حادثة الـ force-push — أُبقيها لأن الحادثة التي ولّدتها لا تزال أحدث حدث موثّق في تاريخ
هذا الريبو، وأي خطة جديدة تتجاهلها تكرر نفس الخطأ:

- **ممنوع نهائيًا** `git push --force` أو `-f` على `main` تحت أي ظرف، بأي مرحلة، بأي وكيل.
- **ممنوع نهائيًا** حذف أي مشروع Vercel أو فك ربط أي دومين بدون عرض الخطة والحصول على موافقتك
  الصريحة المنفصلة (رسالة وحدها، لا ضمن موافقة عامة على خطة أكبر).
- **ممنوع نهائيًا** `git reset --hard` لأي كوميت أقدم من آخر نقطة موثّقة "تم التحقق منها".
- **ممنوع نهائيًا** أي `DROP TABLE` / `TRUNCATE` / migration هدّامة على قاعدة Neon **الإنتاجية**
  دون: نسخة احتياطية موثّقة + تنفيذ أولاً على فرع Neon تجريبي (انظر §6) + موافقتك.
  أي عملية بها الكلمات "احذف الكل / امسح / استبدل الكل" بمشروع Vercel أو Neon أو Git = بوابة
  موافقة إلزامية بذاتها.
- **كل عمل يتم في فرع feature منفصل + Pull Request** — لا كوميتات مباشرة على `main`.
- **لا "تم" بدون دليل حرفي**: رابط فرع فعلي، رابط deployment فعلي، استجابة `curl` فعلية (200 لا
  404)، ناتج `pytest`/`npm run build`/`npx tsc --noEmit` كاملاً منسوخًا لا ملخّصًا. أي وكيل يكتب
  "تم الإصلاح" أو "يعمل الآن" بدون الدليل المطلوب يُعتبر تقريره مرفوضًا تلقائيًا ويُعاد له العمل.
- **تغييرات جراحية**: عدّل أقل عدد ملفات ممكن لتحقيق الهدف، لا تُعِد كتابة ملف كامل إن كان تعديل
  سطرين كافيًا، ولا تكسر أي مسار يعمل حاليًا أثناء إصلاح غيره.
- في نهاية كل مرحلة: تقرير Markdown بصيغة "المشكلة ← الملف/السطر ← الإصلاح ← دليل التحقق"
  (نفس صيغة `docs/remediation-plan.md` الموجودة أصلاً في الريبو — استمر عليها، لا تخترع صيغة جديدة).

## 2. نتائج الفحص الفعلي (Audit Findings)

كل نقطة أدناه مؤكدة بـ `grep`/تشغيل فعلي، وليست تخمينًا.

### 2.1 حالة Git والحادثة السابقة
- الفرع `main` الحالي هو نتيجة عملية ترميم جزئية بعد force-push دمّر هجرة Next.js الكاملة
  (`smartbot-incident-recovery-roadmap.md`). تقرير الترميم (`delivery-report-smartbot-restoration.md`)
  يوثّق استعادة 9 مسارات أساسية + 22 صفحة داشبورد، لكن يترك 9 صفحات كواجهات فارغة غير متصلة
  بأي API حقيقي: **marketing, ads, reports, autoreply, notifications, tools, billing, support, leads**.
- **لا تثق بأي من الملفات التالية كوصف للحالة الحالية** — كلها أقدم من آخر إعادة بناء وتحتاج
  إعادة تحقق حرفي في Phase 0 أدناه قبل استخدامها كمرجع: `docs/remediation-plan.md`
  (2026-07-16، مولّد من تدقيق 40 وكيل)، `docs/audit/2026-07-19-live-comparison.md`،
  `pricing-snapshot.md`, `bot-smart-link-ly-snapshot.txt`. هذه وثائق تاريخية مفيدة كسياق فقط.

### 2.2 تناقض حرج في طوبولوجيا النشر (يجب حسمه قبل أي عمل frontend)
- **يوجد ملفا `vercel.json` متعارضان:**
  - الجذر (`/vercel.json`): `framework: "fastapi"`, يبني الـ Next.js export ثم ينسخه إلى
    `fb_dashboard/static`، ويُشغّل كل شيء عبر دالة بايثون واحدة `api/index.py` — أي أن Next.js
    **لا يُنشر كتطبيق Next.js حي إطلاقًا**، بل كملفات HTML/JS ثابتة تُقدَّم عبر FastAPI.
  - `fb_dashboard/frontend/vercel.json`: `framework: "nextjs"`, `outputDirectory: ".next"` —
    هذا هو إعداد نشر Next.js **الأصلي/الحي** الذي يفترض أن Vercel تُشغّل Next.js runtime كاملاً.
  - `CLAUDE.md` يقول إن هناك **مشروعي Vercel منفصلين** (`smart-bot-api` و `smart-bot-frontend`)
    على نفس الريبو — وهذا الملفان يخدمان مشروعين مختلفين فعلاً، لكن لا يوجد أي توثيق حاليًا
    يوضح: أيهما يخدم فعليًا `bot.smart-link.ly`؟ وهل كلاهما نشط أم أحدهما ميت منذ الحادثة؟
- **تناقض تقني إضافي داخل مشروع frontend نفسه:** `next.config.ts` يضبط `output: "export"`
  (تصدير ثابت بالكامل، لا خادم Node/Edge وقت التشغيل) بينما `middleware.ts` موجود ويحتوي منطق
  حماية فعلي (بوابة تسجيل الدخول لـ `/admin` و `/dashboard`، رؤوس CSP/HSTS). **الـ middleware لا
  يمكن أن يعمل في وضع `output: export`** لأنه يتطلب خادمًا وقت الطلب وهذا الوضع لا ينتج واحدًا.
  إن كان مشروع `smart-bot-frontend` (بإعداد `framework: "nextjs"`) هو من يُستخدم فعليًا، فإما أن
  البناء يفشل صراحة على هذا التعارض، أو أن Vercel تتجاهل الـ middleware بصمت — **في الحالتين
  حماية `/admin` و `/dashboard` قد تكون غير فعّالة في الإنتاج ولا أحد يعرف ذلك حاليًا** لأن CI
  لا يُشغّل `npm run build` إطلاقًا (`.github/workflows/ci.yml` يُشغّل `tsc --noEmit` فقط).
  **هذا أول بند يجب التحقق منه بدليل بناء حرفي قبل أي شيء آخر في الواجهة.**
- إثبات إضافي: عند تشغيل `runner.py` محليًا بدون بناء Next.js أولاً، السيرفر يخدم بصمت ملفات
  Vite/SPA **قديمة ومحفوظة في git** (`fb_dashboard/static/index.html` + حزم `index-*.js`)
  بدلاً من أي تحذير — لأن `STATIC_DIR` يُقرأ حرفيًا كما هو دون تحقق من كونه ناتج Next.js فعلي.

### 2.3 دَين تقني: نظام هجرة قاعدة بيانات ثلاثي متوازٍ (خطر انحراف Schema حقيقي)
ثلاث آليات هجرة غير منسّقة تتعايش حاليًا في نفس الريبو:
1. **Alembic** (`alembic/versions/001_initial.py`, `002_indexes.py`) — الآلية "الرسمية".
2. **SQL خام يدوي** (`fb_dashboard/migrations/001_neon_verify.sql`, `002_saas_migration.sql`) —
   غير مسجَّل في جدول إصدارات Alembic، لا طريقة تلقائية للتحقق من كونه طُبِّق على Neon الفعلية أم لا.
3. **سكربت بايثون منفصل** (`fb_dashboard/migration.py`) يُعدّل SQLite محليًا مباشرة عبر
   `sqlite3.connect` و `ALTER TABLE` يدويًا، خارج Alembic كليًا، ولا يعمل أصلاً على Postgres.
**يجب توحيدها في Alembic فقط** بعد مطابقة فعلية بين ما في `002_saas_migration.sql` وحالة
Neon الحية عبر `information_schema`، ثم أرشفة الملفين الآخرين. مفصّل في §4 (Phase 4).

### 2.4 ملفات ثابتة ميتة محفوظة في git (تخالف قواعد المشروع نفسها)
- `CLAUDE.md` ينص حرفيًا: *"لا Vite/SPA remnants"*. رغم ذلك، **80 ملفًا** تحت
  `fb_dashboard/static/` (git-tracked) هي بناء Vite قديم (`assets/*.js` بأسماء hash قصيرة،
  `index.html` مفرد — لا وجود لمجلد `_next/`)، بالإضافة لمجلد `public/static/` عند جذر الريبو
  (95 ملفًا، بناء Vite مختلف تمامًا بـ hashes مغايرة — أي نسخة ثالثة متضاربة!) **غير مُشار إليه
  في `runner.py` إطلاقًا** (المونت الوحيد هو `fb_dashboard/static`، لا `public/`) — احتمال كبير
  أنه ميت 100%، يحتاج فقط تأكيد بـ curl على مسار منه في الإنتاج قبل حذفه.
- `fb_dashboard/routers/payments.py.bak` محفوظ في git بجانب `payments.py` الفعلي — ملف نسخة
  احتياطية لا داعي له في نظام تحكم إصدارات أصلاً.
- مرجع hardcoded لدومين Render قديم (`smartbot-6lxo.onrender.com`) داخل
  `fb_dashboard/routers/webhooks.py` كـ fallback نهائي — بقايا منصة استضافة سابقة.
- `VERIFY_TOKEN` في نفس الملف له قيمة افتراضية مكشوفة `"smartbot_verify_123"` عند غياب متغير
  البيئة — يجب أن يفشل بصلابة (fail-fast) بدل قيمة افتراضية تخمينية، بنفس نمط `config.py`
  الذي يرفض الإقلاع بدون `SECRET_KEY`/`FERNET_KEY`/`CRON_SECRET`.
- `.specify/memory/constitution.md` أداة spec-kit مثبَّتة لكن **لم تُملأ إطلاقًا** — لا تزال
  القالب الفارغ الافتراضي بالكامل.
- CI (`ci.yml`) يُشغّل `ruff check` و `tsc --noEmit` فقط — **لا يُشغّل `pytest` ولا
  `npm run build` ولا أي اختبار E2E**. هذا يعني أن مشكلة `output:export` + `middleware.ts` أعلاه،
  وأي انكسار بناء مستقبلي، **لن يوقفهما CI إطلاقًا حتى بعد هذه الخطة** ما لم يُصلَح.

### 2.5 عزل المستأجرين (تحقّق إيجابي — لا تكسره)
فحصت تحديدًا مشكلة الـ Singleton التي ذكرها تقرير الحادثة (عودة `BotEngine` كنسخة مشتركة بين كل
المستأجرين). **الحالة الحالية سليمة**: `_services.py` يستخدم `_bot_engines: dict[int, BotEngine]`
مفهرسًا بـ `tenant_id`، وكل استدعاء لـ `BotEngine(...)` في الكود يمرر `tenant_id` فعليًا. هذه
نقطة حرجة للحفاظ عليها حرفيًا في كل عمل لاحق — أي كود جديد (بما فيه محرك MCP الجديد) **يجب** أن
يمرّر ويحترم `tenant_id` في كل عملية، بلا استثناء.

### 2.6 تحليل `facebook-mcp-server` (الأساس المطلوب اعتماده)
فحصت الكود كاملاً (4 ملفات، ~250 سطرًا، رخصة MIT، آخر تحديث حديث). القدرات والحدود الفعلية:

**ما يقدّمه فعليًا (34 أداة MCP):** نشر/تحديث/حذف منشورات، منشورات مجدولة، نشر صور، الرد على
تعليقات وحذفها وإخفاءها/إظهارها (فرديًا وبالجملة)، جلب تعليقات ومنشورات وردودها، إحصائيات منشور
كاملة (impressions/engaged/clicks/reactions بكل أنواعها/shares)، عدد متابعي الصفحة، أكثر
المعلّقين تفاعلاً، رسالة خاصة لمستخدم واحد، رابط دائم للمنشور، معلومات الصفحة الموسّعة.

**حدوده الحقيقية (يجب معرفتها قبل اعتماده):**
- **مستأجر واحد فقط**: `config.py` يقرأ `FACEBOOK_ACCESS_TOKEN`/`FACEBOOK_PAGE_ID` كثوابت
  عامة على مستوى الوحدة (module-level) عبر متغيرات بيئة — **لا يوجد مفهوم "مستأجر" إطلاقًا**.
  اعتماده كما هو حرفيًا = فقدان الـ multi-tenancy الموجود حاليًا في SmartBot بالكامل. هذا وحده
  يمنع "التبني الحرفي" كخيار مطروح جديًا — مفصّل في §3.1.
- **متزامن (sync) بالكامل**: يستخدم `requests` لا `httpx`/`asyncio` — غير متوافق مباشرة مع حلقة
  أحداث FastAPI بدون تشغيله في thread pool، وهذا يُبطل أي كسب في الأداء.
- **صفر معالجة أخطاء**: `facebook_api.py._request` يُعيد `response.json()` حرفيًا دون التحقق من
  `status_code` أو من وجود مفتاح `error` في استجابة Graph API، ودون أي إعادة محاولة (retry) أو
  احترام لحدود المعدل (rate limits).
- **لا صفحات (pagination)**: `get_posts`/`get_comments` تُعيد الصفحة الأولى فقط من Graph API
  (افتراضيًا 25 عنصرًا) دون متابعة `paging.next`.
- **لا يغطي المحادثات/الرسائل الواردة**: يوجد `send_dm_to_user` فقط، **لا يوجد** ما يعادل
  `get_conversations`/`get_conversation_messages` الموجودين فعلاً في `fb_client.py` الحالي
  ويُستخدمان في صفحة "الرسائل" (`inbox_engine.py`). فجوة تغطية حقيقية يجب سدّها.
- **لا يغطي الإعلانات**: لا أدوات لحسابات الإعلانات/الحملات، بينما `fb_client.py` الحالي فيه
  `get_ad_accounts`/`get_campaigns`/`get_ads` (تُستخدم لصفحة "الإعلانات" الفارغة حاليًا أصلاً).
- **لا يستقبل Webhooks إطلاقًا**: وهذا متوقع ومنطقي (خوادم MCP أدوات يستدعيها وكيل، لا مستقبلات
  أحداث) — استقبال ويبهوك فيسبوك ومعالجته (`webhooks.py` الحالي) يبقى مسؤولية SmartBot نفسها،
  والمحرك الجديد يُستدعى **بعد** وصول حدث الويبهوك، لا بدلاً منه.
- **`filter_negative_comments` ساذجة**: قائمة كلمات إنجليزية ثابتة فقط (`bad, terrible,
  hate...`) — عديمة الفائدة لمنتج عربي أولاً. SmartBot الحالي فيه بالفعل تصنيف نوايا أذكى
  (`enhanced_intent.py`) يجب الإبقاء عليه/دمجه بدل الاعتماد على هذا الفلتر.
- **نقل stdio فقط في الإعداد الافتراضي**: مصمم لـ Claude Desktop عبر `uv run ... server.py`
  (عملية فرعية طويلة العمر) — هذا النمط **لا يعمل مباشرة** داخل دالة Vercel serverless (بدون
  عملية أب طويلة العمر تستضيفه). مكتبة `mcp.server.fastmcp.FastMCP` تدعم أيضًا نقل
  `streamable-http`، وهذا هو ما يجب اعتماده لأي تعريض MCP خارجي حقيقي (مفصّل في §3.1).

### 2.7 تحليل LiveCharts2 (استفادة تصميمية فقط — ليست تبعية كود)
مكتبة رسوم بيانية لـ **.NET/C#** (WPF, MAUI, Blazor, WinUI, Avalonia...) عبر محرك رسم Skia.
**لا يمكن استيراد كودها إطلاقًا** في مكدّس Python/Next.js — أي محاولة "استخدامها" حرفيًا كتبعية
مرفوضة تقنيًا من الأساس. القيمة الحقيقية هنا هي **بصرية/سلوكية فقط**: حركة انتقال سلسة بين نقاط
البيانات، مؤشرات دائرية (gauges)، رسوم خطية/مساحية حيّة الإحساس، تلميحات (tooltips) أنيقة.
SmartBot يستخدم بالفعل `recharts` (^3.9.2، حديثة) و`framer-motion` (^12.42.0) — **كافيان تمامًا**
لتحقيق نفس مستوى الحِرفية البصرية عبر طبقة مكوّنات مخصصة جديدة (`components/charts/`) بدل جلب
مكتبة رسوم جديدة كليًا (تجنبًا لتضخيم الحزمة بلا داعٍ). مفصّل في §3.4 و Phase 6.

### 2.8 تحليل scroll-craft (أداة Claude Code + دستور تصميم، وليس مكتبة تشغيل)
هذا ليس مكتبة JS تُستورد — هو **skill/plugin لـ Claude Code** يبني صفحات هبوط تسويقية طويلة
مدفوعة بالتمرير (scroll-driven) بمعايير حِرفية صارمة، مع فاحص آلي (headless browser) يتحقق من
التباين، ووصول الرسوم لكامل العتامة، وعدم وجود "scroll ميت". أهم ما فيه للاستخدام هنا ليس تشغيله
حرفيًا بل **دستور التصميم** الذي يفرضه (يُعتمد كقواعد ملزمة لكامل إعادة التصميم، لا لصفحة الهبوط
فقط): سقف خطّين للخطوط، تباعد بمقياس ثابت 4px، ستة أدوار لونية + لون تمييز واحد، خمس أدوات عمق لا
أداة واحدة، و**قائمة رفض صريحة**: شبكات بطاقات-ميزات متطابقة، عدادات `01/06`، إشارات scroll
زخرفية، تدرجات لونية بنفسجية نمطية لـ AI، لوحة "حرفي" بني/كريمي المستهلكة. هذه القائمة تُطبَّق
حرفيًا كقيود على كل عمل تصميم في هذه الخطة (Phase 6 و Phase 8).
**الاستخدام العملي المزدوج الموصى به:**
1. تُثبَّت فعليًا كـ plugin في Claude Code (`/plugin marketplace add nateherkai/scroll-craft`)
   وتُستدعى حرفيًا لإعادة بناء صفحات الهبوط/التسعير/العرض التوضيحي العامة فقط (Phase 8) — لأنها
   مصممة تحديدًا لهذا النوع من الصفحات ذات السرد الواحد المستمر.
2. مبادئها التصميمية (وليس تشغيلها) تُستخرج كقواعد نظام تصميم عامة (Phase 6) تُطبَّق على كامل
   الداشبورد، بما فيه الصفحات التي لن تُبنى بـ scroll-craft نفسها.

## 3. القرارات المعمارية الحاسمة (بوابة موافقة قبل أي كود)

### 3.1 محرك فيسبوك — القرار: **إعادة بناء احترافي حول عقد facebook-mcp-server، لا تبنٍّ حرفي**

**الخيار المرفوض وسبب رفضه:** تشغيل `facebook-mcp-server` كما هو حرفيًا "كأساس ومحرك للمشروع
كامل" (بمعناها الحرفي: استيراده كتبعية وتشغيله فعليًا) يعني: فقدان تعدد المستأجرين بالكامل
(نقطة §2.6 الأولى) — وهذا انحدار خطير في منتج SaaS قائم بالفعل على هذا التعدد (جدول `Tenant`،
اشتراكات، خطط أسعار). كما يعني فقدان الرسائل/المحادثات، فقدان الإعلانات، صفر معالجة أخطاء، صفر
صفحات نتائج (pagination)، وفلتر مشاعر عديم الفائدة بالعربية. هذا ليس "أساسًا ومحركًا مثاليًا
واحترافيًا" — هو تراجع.

**القرار الموصى به (نفّذه ما لم تُعلمني برفضك):** اعتماد facebook-mcp-server **كعقد واجهة
(interface contract)** لا كتبعية:
1. بناء حزمة جديدة `fb_dashboard/facebook_engine/` بمنطق **async كامل** (`httpx.AsyncClient`)،
   **واعية بالمستأجر** (كل دالة تأخذ `tenant_id`/token مشفّر مثل البنية الحالية عبر `_crypto.py`)،
   تُغطّي **كل الـ 34 أداة** من facebook-mcp-server بنفس الأسماء/التوقيعات كنقطة انطلاق، **زائد**
   سد الفجوات: صفحات نتائج كاملة، إعادة محاولة/backoff، احترام rate limits، معالجة أخطاء Graph
   API الحقيقية، بالإضافة لكل ما هو موجود حاليًا في `fb_client.py` ولا وجود له في fb-mcp
   (المحادثات، الإعلانات).
2. تعريض نفس الحزمة **كخادم MCP حقيقي مستقل** (`mcp.server.fastmcp.FastMCP`، نقل
   `streamable-http` لا `stdio` — متوافق مع بيئة سحابية) — بحيث تصبح "محرك المشروع" حرفيًا بمعنى
   أن **كل** عملية فيسبوك في التطبيق (الويبهوك التلقائي، لوحة التحكم، الوكيل الذكي) تمر عبر نفس
   الحزمة الواحدة، وتصبح أيضًا قابلة للاستدعاء من Claude Desktop/Claude Code مباشرة لأغراضك
   التشغيلية الخاصة.
3. استبدال أدوات الوكيل الذكي المكتوبة يدويًا حاليًا (`agent_tools.py` — 9 أدوات JSON schema
   يدوية في `AgentEngine._execute`) لتستدعي أدوات نفس محرك MCP الجديد بدل التكرار — توحيد حقيقي
   لـ"يد" الوكيل الذكي مع الأدوات المُعرَّضة خارجيًا.
4. نقل منطق الرد التلقائي (`bot.py` — `ReplyPipeline`, `IntentAwareMatcher`) والفلترة الذكية
   للتعليقات (`enhanced_intent.py`) دون تغيير جوهري — تبقى **فوق** محرك MCP الجديد، تستدعيه، ولا
   تُستبدل بفلتر الكلمات المفتاحية الساذج من fb-mcp.

هذا القرار يُبقي روح طلبك (facebook-mcp-server هو "الأساس" — عقده، تسمياته، وتعريضه كـ MCP هو
فعلاً قلب النظام الآن) دون كسر الإنتاج الموجود. **إن كنت تقصد فعلاً التبني الحرفي بمستأجر واحد
(أي أن SmartBot سيدير صفحة فيسبوك واحدة فقط لا SaaS متعدد المستأجرين)، أخبرني الآن صراحة قبل
Phase 2 — القرار سيتغير جذريًا.**

### 3.2 طوبولوجيا Vercel — القرار: **مشروع واحد، لا مشروعين**

توصيتي: توحيد النشر في **مشروع Vercel واحد** بإعداد `framework: "nextjs"` (إعداد
`fb_dashboard/frontend/vercel.json` الأصلي، لا إعداد الجذر)، مع تشغيل Next.js في وضعه الطبيعي
(بدون `output: "export"`) بحيث يعمل الـ middleware فعليًا، والـ API routes تُستضاف كدوال Vercel
Python منفصلة عبر `rewrites` بدل تحويل Next.js بالكامل لملفات ثابتة تُقدَّم من بايثون. هذا يحل
تناقض §2.2 نهائيًا، ويُبقي domain واحد فقط (`bot.smart-link.ly`) بدل الازدواجية الحالية بين
`bot.smart-link.ly` (يبدو معطلاً/غير مربوط منذ الحادثة) و`api.smart-link.ly` (يخدم SPA قديمة).
**التحقق الفعلي من إمكانية هذا التحويل (خاصة مع دوال Python الحالية) هو أول عمل في Phase 5 —
هذا القرار قابل للتراجع إن أظهر التحقق الفعلي عوائق حقيقية، ولن يُنفَّذ أي حذف لمشروع Vercel
قائم قبل نجاح المشروع الموحّد الجديد جنبًا إلى جنب والتحقق منه بـ curl حي.**

### 3.3 قاعدة البيانات — Neon Postgres، بفروع (branches) لا بيئة واحدة
توصيتي: اعتماد ميزة **Neon branching** (فرع `production` + فرع `preview`/`development` منفصل
يُنسخ من الإنتاج عند الحاجة) بدل قاعدة تطوير SQLite محلية منفصلة تمامًا عن الإنتاج كما هو الحال
الآن — هذا يُقلّل مفاجآت "يعمل محليًا، ينكسر في Neon" (فروقات SQLite/Postgres). مفصّل في §6.

### 3.4 النظام البصري — طبقة تصميم موحّدة قبل أي صفحة
توصيتي: **لا تُعاد كتابة أي صفحة قبل بناء طبقة "design tokens + primitives" موحّدة أولاً**
(Phase 6.1) تستوعب دستور scroll-craft (§2.8) ومكوّنات الرسوم المستلهمة من LiveCharts2 (§2.7)،
ثم تُطبَّق هذه الطبقة على الهيكل العام (shell/sidebar/topbar)، ثم على كل صفحة. العمل صفحة-بصفحة
بدون أساس موحّد أولاً هو بالضبط ما أنتج "double sidebar" و"double branding" في تاريخ هذا الريبو
(`docs/remediation-plan.md` §0.3، §2.1).

## 6. خطوات Neon Postgres (تفصيلية لـ Phase 4/5)

1. **لا تُنشئ قاعدة بيانات جديدة من الصفر** — قاعدة الإنتاج الحالية موجودة ومتصلة (`DATABASE_URL`
   يشير إليها بالفعل حسب `.env.example`). الهدف توحيد وتنظيف، لا استبدال.
2. أنشئ **فرع Neon جديد** (`neonctl branches create --name preview-rebuild --parent production`
   أو من لوحة Neon) — يُنسخ فيه شكل الإنتاج الحالي فعليًا (copy-on-write، سريع ورخيص في Neon).
3. كل migration جديدة من Phase 4.2 تُطبَّق **على هذا الفرع أولاً**: `alembic upgrade head` مع
   `DATABASE_URL` مؤقتًا مُشارًا لسلسلة اتصال الفرع التجريبي (وليس متغير بيئة الإنتاج).
4. تحقق كامل على الفرع التجريبي: تشغيل التطبيق كاملاً باتصال به، فحص كل مسار API يلمس القاعدة.
5. فقط بعد نجاح كل ما سبق ✅ + موافقتي الصريحة: تُطبَّق نفس الـ migration على فرع `production`
   الفعلي، ويُوثَّق ذلك بناتج `alembic upgrade head` الحرفي منسوخًا كاملاً.
6. اربط فرع Neon الجديد (إن استمر استخدامه) بمشروع Vercel Preview environment تحديدًا — بحيث كل
   PR مستقبلي يحصل تلقائيًا على قاعدة معزولة عن الإنتاج، بدل الاعتماد على SQLite محليًا فقط الذي
   يُخفي فروقات Postgres الحقيقية (نقطة §3.3).
7. فعّل نسخ Neon الاحتياطية التلقائية (point-in-time recovery) إن لم تكن مفعّلة — يُتحقق منه
   كبند صريح ضمن Phase 0.4 قبل أي migration جديدة إطلاقًا.

## 7. خطوات Vercel (تفصيلية لـ Phase 5)

1. **لا تحذف أي مشروع قائم أولاً.** أنشئ مشروع Vercel جديدًا (اسم مقترح: `smart-bot` موحَّد)
   مربوطًا بنفس الريبو، فرع مصدر مؤقت (`feature/unified-deploy`)، **بدون** ربط دومين حقيقي بعد.
2. اضبط عليه `framework: Next.js` تلقائيًا (بحذف `output: "export"` بعد تأكيد 5.1 من الخريطة
   أعلاه)، ودالة Python لـ API عبر `vercel.json` بـ `rewrites` من `/api/*` فقط (لا كل المسارات).
3. انسخ كل الأسرار من §5 لبيئتي Production و Preview على المشروع الجديد (لا تُدخل قيم حقيقية في
   أي ملف/كوميت — عبر `vercel env add` أو لوحة التحكم فقط).
4. انشر (deploy) على دومين Vercel المؤقت (`*.vercel.app`) أولاً، ونفّذ فحص curl حي كامل مطابق
   لجدول `delivery-report-smartbot-restoration.md` (9 مسارات + الصفحات التسع المكتملة حديثًا).
5. فقط بعد ✅ كامل + موافقتي: انقل الدومين `bot.smart-link.ly` من المشروع القديم إلى الجديد عبر
   Vercel (`vercel domains` أو من لوحة التحكم) — هذه لحظة تحويل حقيقية للإنتاج، تحتاج نافذة صيانة
   قصيرة معلنة، ليست عملية صامتة.
6. راقب الأخطاء 15–30 دقيقة بعد التحويل (Vercel logs حية)، مع خطة تراجع فورية: إعادة ربط الدومين
   للمشروع القديم إن ظهر أي انكسار، فورًا وبدون تردد.
7. فقط بعد استقرار موثّق (24 ساعة بلا أخطاء حرجة) + موافقتي الصريحة المنفصلة: أرشفة/حذف المشروع
   القديم غير المستخدم، مطابقةً لقاعدة §1.

## 8. تعريف الإنجاز النهائي (Definition of Done)

المشروع "منتهٍ" لهذه الخطة فقط عند تحقق **كل** ما يلي بدليل حرفي، لا بتقرير وكيل:
- [ ] استجابة `curl` فعلية 200 على كل صفحة من 23 صفحة داشبورد + كل صفحة عامة، على الدومين النهائي.
- [ ] `npm run build` و `pytest` و Playwright E2E جميعها خضراء ضمن CI فعليًا (لا محليًا فقط).
- [ ] رد تلقائي فعلي على تعليق حقيقي على صفحة فيسبوك اختبارية عبر محرك MCP الجديد، موثّق بلقطة/سجل.
- [ ] لا استدعاء واحد متبقٍ لـ `fb_client.py` القديم في كامل الكود (`grep` يُعيد صفرًا).
- [ ] هجرة قاعدة بيانات واحدة موحَّدة (Alembic فقط)، مطابَقة فعليًا مع Neon الإنتاجية.
- [ ] مشروع Vercel واحد فقط نشِط، القديم مؤرشف بموافقة صريحة موثّقة.
- [ ] صفر ملفات Vite/SPA ميتة في git (`fb_dashboard/static` القديم، `public/static`، `*.bak`).
- [ ] كل الصفحات التسع الناقصة تعرض بيانات حقيقية لا حالة "قيد التطوير".
- [ ] `docs/design-refuse-list.md` مطبَّق ومُتحقَّق منه على كل صفحة (لا نمط AI نمطي متبقٍ).
- [ ] `CLAUDE.md` مُحدَّث ليعكس الواقع الجديد فعليًا، والوثائق التاريخية المتضاربة مؤرشفة بوضوح.
