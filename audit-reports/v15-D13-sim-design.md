## 3) آلية الادعاءات المفروضة (fail-the-battery) — إغلاق D7-F1

### 3.1 السلوك الجديد لـ `checkClaim` (نفس التوقيع — صفر تعديل في 55 موقع استدعاء)

```
checkClaim(persona, claim, sql, args, predicate, expected, extra)
  1. ينفّذ الاستعلام/المسند كالسابق ويسجّل الصف في sim-claims.json (JSONL)
  2. إذا ok = true → يعيد الصف (كما في v14)
  3. إذا ok = false:
     أ. إن كان معرّف الادعاء في findings/sim-findings.json → يوسم السجل "allowlisted"
        + يطبع «FINDING موثق: <id>» + يسطره في sim-findings-live.json → الاختبار يستمر
        (المحصلة تُحسب منفصلة: findings ≠ فشل)
     ب. وإلا وSIM_ENFORCE_CLAIMS=1 (الافتراضي) →
        throw new Error(`ادعاء أحمر غير موثق: ${persona}/${claim} — متوقع: ${expected} | فعلي: …`)
        → يفشل الاختبار → playwright exit ≠ 0 → البطارية حمراء
     ج. SIM_ENFORCE_CLAIMS=0 (تشخيص فقط) → تحذير بلا رمي
  4. أخطاء الاستعلام نفسها (query error) تُعامل كأحمر: تسجيل + نفس مسار الإنفاذ (لا ابتلاع)
```

### 3.2 البوابة في السكربت (`v15_sim_local_battery.sh`)

```
بعد playwright:
  red      = عدد "ok":false غير الموسومة allowlisted
  findings = عدد الموسومة
  findingClosed = عدد إدخالات قائمة السماح التي صارت خضراء في هذه الجولة
  CLAIMS_EXIT = (red > 0) ? 1 : 0
  exit النهائي = (PW_EXIT ≠ 0 || CLAIMS_EXIT ≠ 0) ? 1 : 0
```

طبقتان (رمي داخل الاختبار + خروج السكربت) بحيث فشل أي منهما يحمرّ البطارية — يقتل نمط «سجّل ولا تُنفّذ» نهائياً، ويُبقي تشغيل أي مواصفة منفردة صادقاً (`npx playwright test -c playwright.sim.config.ts e2e/sim-p10…`).

### 3.3 قائمة السماح `sim/findings/sim-findings.json` (البذرة الأولية)

كل إدخال: `{ "id", "finding" (مرجع تقرير D), "expires": "v15", "owner": "E-wave" }` — TTL بجولات لا تواريخ؛ السكربت يطبع تنبيهاً لأي إدخال تجاوز جولته.

| id | المرجع | الحالة المتوقعة اليوم (حمراء) | متى يُقلب أخضر ويُحذف |
|---|---|---|---|
| `p08-crm-lead-r3` | v14 §6 R3 | خطوة CRM لا تكتمل بتوكن زائف | قياس إنتاج بعد توكن حقيقي (خارج البطارية المحلية — expires: prod) |
| `p10-dm-gate` | D2-H1 | DM يُرسَل لخطة بلا has_dm | E-wave يفرض has_dm |
| `p10-broadcast-gate` | D2-H1 | البث يُرسَل لخطة بلا has_broadcast | E-wave يفرض has_broadcast |
| `p10-max-replies` | D2-H1 | الردود لا تتوقف عند السقف | E-wave يفرض max_replies |
| `p10-replies-used-comments` | D2-H3 | مسار تعليقات webhook لا يزيد replies_used | E-wave يوحّد العدّ |
| `p13-ssrf-receipt-dns` | D6-H2 | جلب إيصال بمضيف DNS داخلي يمرّ | E-wave يضيف حل DNS للحارس |
| `p13-cron-query-token` | D6-M3 | `?token=` مقبول (200) | E-wave يزيل مسار الاستعلام |
| `p13-changepw-429` | D6-M4 | لا سقف per-account على change-password | E-wave يضيف السقف |
| `p13-register-race-500` | D1-H4 (أشقاء) | تسجيل متزامن لنفس الاسم → 500 خام | E-wave upsert/begin_nested |
| `p10-free-funnel` | D4-C1 | الخطة المجانية تنتهي بمسدود نافذة الدفع | E-wave يصلح مسار التفعيل المجاني |

**كاشف الانقلاب (ابتكار):** أي إدخال سماح صار أخضر يُسجَّل `findingClosed` في تقرير الجولة → إشارة فورية للمنسّق لحذف الإدخال وقلب العقد صارماً (هذا هو مسار إغلاق D13-F1 نفسه: الإصلاح → الادعاء يخضرّ → يُحذف الإدخال → الصرامة افتراضية).

### 3.4 القرارات الصارمة (STRICT)

| القرار | الآلية |
|---|---|
| **SIM_STRICT_409=1 افتراضياً** (بعد إغلاق D13-F1) | السكربت يصدّره=1؛ p06 يقرؤه أصلاً (سطر 24) فيصبح 409 حصراً + detail عربي. مسافة تنفس: `SIM_STRICT_409=0` لتشخيص ما قبل الإصلاح فقط (موثق في رأس السكربت). إن أُغلق D13-F1 قبل أول تشغيل v15، لا يدخل قائمة السماح إطلاقاً |
| **SIM_ENFORCE_CLAIMS=1 افتراضياً** | البند 3.1 — `=0` تشخيص فقط |
| **p08 bot_logs: `after > before`** | عدد أحداث الجولة معروف سلفاً (لا `>=` البديهي — D7-F7) |
| **p08 cooldown: قياس R3 صادق** | كلا التعليقين محفوظان في DB + الرد DB-first مرة واحدة أو finding R3 — لا بديهية `≤1` مع صفر صفوف (D7-F2). توسعة اختيارية إن نفّذ E-wave علم `SIM_FAKE_GRAPH`: يصبح العدّ حقيقياً على ردود فعلية |
| **مراسي الفواتير/KPI قوية** | toContain(اسم الخطة/المبلغ/الحالة) + claim على صف subscription_payments (D7-F5/F8/F9) |

## 4) الشخصيات الأربع عشرة

### 4.1 الشخصيات المحفوظة (p01-p08) — «الاستثمار»

تبقى حرفياً كما في v14 (48 اختباراً/~130 خطوة) بلا مسّ لترتيبها أو اعتمادياتها (توكنات القرص، `.admin_token`، ترتيب p08/p04/p05 على p02). التعديلات الجراحية الثلاثة فقط:

1. **p02 (منال المشتركة):**
   - خطوة الدفع (t11-14): بعد النقر «ادفع الآن» — فحص فوري `button[disabled]`/`aria-disabled` أثناء POST + عدّ استجابات `/api/subscriptions` = 1 (نقرة واحدة)؛ ثم إرسال نقرتين متزامنتين عبر `races.doubleClickSubmit` → claim `p02-pay-single-submit` (POST واحد + payment_id واحد).
   - t19-20: استبدال `billText.length > 200` بـ `toContain(اسم الخطة)` + `toContain('د.ل')` + claim على `subscription_payments` (المبلغ/الحالة/المستأجر).
   - t22: مسار fallback الجلسة يُسجَّل claim وصفي `p02-session-channel=stable|recovered` (يكشف flicker بدل كتمه — D7-F17).
2. **p04 (منال العائدة):** مرساة t9-11 تُقيَّد بنطاق عنصر الشحنة (إسقاط فرع «ليبيانا» الدائم التحقق) + claim اتساق: بعد قرار cancelled → `payment.status` و`tenants.subscription_status` و`users.subscription_status` بلا حالة نصف مختلطة.
3. **p08 (فاطمة زبونة البوت):** البندان 3.4 أعلاه (bot_logs صارم + cooldown صادق).

(p01/p03/p05/p06/p07: بلا تعديل — p06 يصرّم عبر البيئة فقط.)

### 4.6 p13 — «مروان المهاجم الموسّع» (سباقات + bidi + SSRF + حدود)
