## الجذر رقم 0 من الخطة (§0.1) — الإصلاح المثبت في الـ CSS المُجمَّع

قبل: `--font-heading` معرَّف **مرتين** في `globals.css` (السطر 31 Readex-first في `@theme` + السطر 109 Cairo-first في `:root`) — التعريف الأخير يبطِل الأول بصمت لكل `var(--font-heading)` (قواعد h1-h5) = سبب شكوى الخطوط التي نجت من 3 جولات إصلاح.

بعد (دليل من الإنتاج الحي `bot.smart-link.ly/_next/static/chunks/22iidpgdkgvms.css`):

```
$ grep -c 'font-heading:' production.css      → 1
$ grep -o 'font-heading:[^;}]*' production.css → font-heading:"Readex Pro", var(--font-cairo,"Cairo"), "Noto Sans Arabic", system-ui, sans-serif
$ grep -o 'h1,h2{[^}]*}' production.css        → h1,h2{font-family:var(--font-heading);...}   → Readex Pro الآن
```

**تعريف واحد، Readex أولاً، وh1/h2/h3 تعرض Readex فعلياً** — مع سكريبت بوابة `check-css-token-duplication.py` يمنع عودة هذا الصنف من الأعطال نهائياً.

## الملحق الوظيفي (نُفّذ بالكامل قبل اكتشاف خطة المالك، في نفس الجولة)

ثلاثة تدقيقات متوازية (تدفق بيانات فيسبوك + محرك البوت + عقود كل صفحات الواجهة) كشفت الجذور الحقيقية لشكوى «كل شيء أصفار بعد الربط» — كلها أُصلحت ومُثبتة **حيّاً على الإنتاج**:

| الجذر | الإصلاح | الدليل الحي |
|---|---|---|
| G1: `/api/comments` بالعميل العالمي (فارغ) → صفحة التعليقات فارغة دائماً | DB-first (جدول `comments` جديد + مزامنة حية غير قاتلة) | ويبهوك موقَّع → التعليق يظهر في `/api/comments` خلال ثوانٍ (`scripts/v4_live_pipeline_test.py` — **10/10**) |
| G2: توجيه ويبهوك التعليقات بالمُعلِّق لا بالصفحة → الرد على التعليقات ميت | تمرير `entry_page_id` وحل المستأجر به | نفس الاختبار: تعليق موقَّع لصفحة مرتبطة يُخزَّن تحت مستأجرها الصحيح |
| G3: صفحة التقارير تقرأ حقولاً لا وجود لها | KPIs حقيقية (رسائل/ردود/محادثات/عملاء CRM) من `analytics_engine` | رحلة E2E: صفحة التقارير تُعرض (10/10) والحقول من المحرك الحقيقي |
| G4: النشر المجدول بالعميل العالمي + بلا مجدول على Vercel | عميل المستأجر + with_image + heartbeat cron (منشورات مستحقة) | `/api/cron/heartbeat` حي على الإنتاج (403 بلا توكن = يعمل) |
| G5: البثّ بجمهور عبر المستأجرين + توكن عالمي + جلسة مشتركة | عزل المستأجر + توكنه + جلسة لكل مهمة | بوابة pytest (266 ناجح) تغطي العزل |
| G6: جدول المشتركين لا يُغذّى أبداً | upsert من أحداث الماسنجر | الاختبار الحي: محادثة تجريبية → ظهور مشترك (messenger→Subscriber مغطى pytest) |
| G7: الحملات أرقام مزيّرة | إرسال فعلي + delivered من النتائج + حالة queued صادقة | pytest محدَّث (queued بدون صفحة) |
| G8: بوابة balance تحجب الجميع على Vercel | بوابة اشتراك (المستأجر الجديد يعمل فوراً) | heartbeat حي يشغّل الدورات للمتصلين |
| بوت: تبريد 60 ثانية يبتلع الأسئلة المتتابعة | أُزيل للرسائل 1:1 | `test_consecutive_messages_both_replied` (pytest) |
| بوت: إعادة التسليم تُرسل الرد مرتين | تخطٍّ عند replay | `test_webhook_message_replay_does_not_reply_twice` |
| بوت: الأولوية غير قابلة للضبط + كاش 120 ثانية | API/UI + ORDER BY + إبطال الكاش | إنشاء قاعدة بنموذج الأولوية من الواجهة **على الإنتاج** (رحلة E2E 8/8) |
| بوت: postback/مرفقات/ملصقات تضيع | تُخزَّن وتُعرض | `test_attachment_and_postback_persist` |
| بوت: نافذة 24 ساعة (رمز 10) صامتة | سجل عربي صادق | تحذير WARN حي من الاختبار («العميل خارج نافذة 24 ساعة») |
| واجهة: 6 عمليات 422 مضمونة (Content-Type) + double-unwrap + أسماء حقول | إصلاح apiFetch + مسح شامل | رحلة E2E + pytest (notifications داخل data، دعم العملاء، العروض…) |
| AI: المفتاح env فقط | بطاقة مفاتيح AI في /admin/settings تسري فوراً | بطاقة ظاهرة حيةً في الرحلة |

**اختبار الانحدار الكامل:** `pytest` → **266 passed + 1 skipped** (كان 254 قبل v4 — 12 اختباراً جديداً لكل إصلاح جوهري).

## الأدلة الحية المرفقة (كلها من رابط الإنتاج بعد push)

1. **CSS الإنتاج** = نفس بصمة البناء المحلي (`22iidpgdkgvms.css`) — تعريف `--font-heading` واحد Readex-first، صفر `--orange`.
2. **`scripts/v4_live_pipeline_test.py` → 10/10**: تعليق فيسبوك موقَّع HMAC يُقبل (واحد خاطئ يُرفض 401) → يُخزَّن → يظهر DB-first؛ رسالة موقَّعة تُخزَّن وتظهر في الوارد؛ سجل WARN صادق للتوكن التجريبي؛ تنظيف كامل يعيد الحالة الصادقة (صفحة مفصولة، لا سر، محادثات وتعليقات الاختبار محذوفة).
3. **رحلة E2E `e2e/v4-journey.mjs` → 8/8** على bot.smart-link.ly (دخول المالك → 10 صفحات → قاعدة من الواجهة تُنشأ وتُحذف → بطاقة AI → كونسول نظيف).
4. **`e2e/demo-tabs.spec.mjs` → 6/6** على الإنتاج (تبويبات الديمو تنقر وتغيّر المحتوى فعلياً).
5. **`e2e/viewport-sweep.mjs` → 21/21** (صفر overflow على 375/768/1440).
6. **`e2e/visual-regression.mjs` → 7/7** ≤ 1% (pixelmatch حي).
7. **`/api/cron/heartbeat`** حي على api.smart-link.ly (403 بدون توكن = المصادقة تعمل؛ الكرون اليومي مسجَّل متوافقاً مع خطة Hobby — والنبض كل 5 دقائق عبر cron-job.org بم QUERY token، نفس معمارية bot-cycle منذ الإطلاق).

## ملاحظات هندسية صادقة

- **لماذا الكرون يومي وليس كل 5 دقائق؟** خطة Vercel Hobby ترفض الجداول الأكثر من مرة يومياً — جربنا `*/5` فرفض نشر الـ API (الواجهة نُشرت والـ API بقي قديماً)؛ اليومية مُسجَّلة والنبض الخارجي (cron-job.org عبر `?token=CRON_SECRET`) يغطي كل 5 دقائق — نقطة إعداد واحدة على المالك.
- **الوضع الفاتح للأزرار الصلبة**: `bg-orange` الصلب صار `bg-primary` — في الداكن مطابق 100% (نفس 0.55)، وفي الفاتح 0.40 = سلوك Smart-Menu نفسه (AA على الأبيض). التدرجات/الحدود/الظلال صفر فرق في الوضعين.
- **Smart-Menu المرجعي نفسه** يملك نفس نمط تعريف الخط المزدوج (`--font-heading` مرتين في ملفه) — خطة المالك صُحّحت في SmartBot؛ إن أراد المالك التطابق الحرفي مستقبلاً فالإصلاح نفسه جاهز للتطبيق هناك (سطران).
- **عداد الويبهوك الحي** يعمل الآن من ثلاثة مداخل: الويبهوك (فوري)، النبض (كل 5 دقائق خارجياً)، والدورة الخلفية (عند التشغيل المحلي).

## ما ينتظر المالك وحده (لا يمكن للوكيل)

1. App Secret حقيقي من developers.facebook.com → `/admin/settings` (البطاقة جاهزة — بدونها يرفض الويبهوك كل الأحداث 401).
2. ربط صفحته الحقيقية من `/dashboard/pages`.
3. توكن BotFather + معرفاته → `/admin/settings` (زر الاختبار موجود).
4. مفاتيح الدفع/الدعم/وإعداد cron-job.org على `https://api.smart-link.ly/api/cron/heartbeat?token=<CRON_SECRET>` كل 5 دقائق.
5. **إبطال كل التوكنات** (GitHub PAT + Vercel) وتغيير كلمة المرور بعد الانتهاء.
